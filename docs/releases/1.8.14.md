# Sky Omega 1.8.14 — DrHook: a rebuilt target stays visible

**Released:** 2026-10-25
**Version bump:** `Directory.Build.props` → 1.8.14 (with these notes)
**Predecessor:** [Sky Omega 1.8.13](1.8.13.md) — DrHook runs on Linux.

## Headline

On Linux, one .NET process whose executable had been deleted or replaced broke DrHook's process listing. A rebuild
replaces the executable, so this was common. The engine's `ProcessInspector.ListDotnetProcesses` threw
`FileNotFoundException`. `drhook_processes`, which had its own copy of the listing, silently left the process out.

The hidden process was usually the one an operator was looking for: a leftover debug target still running an old
build. DRHOOK.md tells you to find those with `drhook_processes`. It happened in a normal session too: rebuilding
`src/DrHook.Mcp` while Claude Code runs the local-source DrHook MCP leaves that server in this state.

From 1.8.14 such a process stays in both listings and is marked `ExecutableDeleted`. See
[finding 93](../../poc/drhook-engine/findings/93-deleted-executable-process-listing.md).

## Fixed

- **The listing no longer throws or hides a process with a deleted executable.** Linux reports the main module as
  `<path> (deleted)`, and reading the version of a file that is gone threw. A new shared per-process read,
  `ProcessIdentity.TryRead`, skips only processes that have exited. It strips the ` (deleted)` suffix, treats a
  missing file as deleted on every platform, and reads the version only from a file that still exists.
- **A main module that can't be read keeps the process listed**, without a path, instead of dropping it.

## Changed

- **`drhook_processes` rows have a new field, `"executableDeleted"`.** When it is true, `"version"` is `"unknown"`,
  and `"path"` is where the executable was.
- **`DotnetProcess` has a new optional parameter, `ExecutableDeleted`** (default `false`). Source that constructs it
  still compiles. Code compiled against 1.8.13 that calls its constructor needs a rebuild.
- **One listing instead of two.** `ProcessAttacher.ListDotNetProcessesAsync`, behind `drhook_processes`, now uses
  `ProcessInspector.ListDotnetProcesses`. As a result the tool also gets the engine's 2-second bound on process
  discovery (DBG-PI-1), so it returns an empty list rather than hanging when discovery stalls.

## Docs

- DRHOOK.md's test table lists every test project with its current count, including DrHook.Viz, DrHook.Wire,
  DrHook.Capture, Mercury.Solid and SkyOmega.Bcl.
- DRHOOK.md's advice on leftover processes mentions the new `executableDeleted` flag.

## Validation

- **New integration test:** `DeletedExecutableListingTest` runs a private copy of the snapshot target, deletes the
  copy's executable, and checks both listings. Run against the old code, it fails with the original
  `FileNotFoundException: … (deleted)`.
- **New unit tests:** 7 in `ProcessInspectorTests`, covering the suffix parsing, a pid that isn't running, and the test
  process itself.
- **zbook:** DrHook.Engine unit tests 174/174, DrHook.Viz 42/42, DrHook.Wire 5/5, DrHook.Capture 1/1. Integration
  suite 17/17 in three runs in a row, with no leftover processes or temp folders. The stale local-source
  `drhook-mcp` server that started the finding is now listed as deleted.
- Earlier the same day on zbook at 1.8.13, Mercury.Tests ran 4722 passed, 0 failed, 6 skipped, Mercury.Solid 25/25
  and SkyOmega.Bcl 12/12. Nothing in Mercury changed in this release.

## Known issues

- **macOS is unverified.** macOS has no ` (deleted)` path, so the fix relies on the missing-file check there. On macOS
  the new test checks only that the process stays listed, not that it is marked. A rebuild that writes a new file at
  the same path probably shows the new file's version, and isn't detected on macOS.
