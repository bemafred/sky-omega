# Sky Omega 1.8.32 — Mercury: grouping and aggregates by §18.2.4 and §18.5

**Released:** 2026-10-29
**Version bump:** `Directory.Build.props` → 1.8.32 (with these notes)
**Predecessor:** [Sky Omega 1.8.31](1.8.31.md) — Mercury: syntax by the grammar, FROM as one merged graph, property
paths by §18.6.

## Headline

**A query level is evaluated in the spec's order.** §18.2.4 runs grouping, aggregates, HAVING, the trailing VALUES and
the SELECT expressions, in that order. §18.2.5 then runs ORDER BY, projection, DISTINCT and the slice. Mercury had
three of these steps in the wrong place:
- It joined the trailing VALUES before grouping.
- It sorted before the SELECT expressions.
- It computed only the SELECT clause's aggregates, not those in HAVING or ORDER BY.

**Every aggregate gives the spec's answer:**
- COUNT counts only bound, non-error values.
- An aggregate's argument can be any expression.
- SUM and AVG have the type of their arithmetic.

**The 5 known W3C failures for the trailing VALUES pass**, so 31 known failures remain (36 at 1.8.31). None of them
is in the SPARQL 1.1 query suites.

## Changed: what queries return

These changes in behavior follow SPARQL. Each was wrong before.

- **A grouped query's trailing VALUES is joined with its groups,** after HAVING and before the SELECT expressions.
  - A grouped query can project a VALUES variable, use it in a SELECT expression, or use it in a CONSTRUCT template.
  - An aggregate no longer counts each solution once per VALUES row. `COUNT(*)` over three solutions with
    `VALUES ?x { 1 2 }` is two rows of 3. It was one row of 6.
- **ORDER BY sorts after the SELECT expressions.**
  - `ORDER BY ?n` over `(COUNT(*) AS ?n)` orders the groups. Before, it kept the order they were first seen in.
  - `ORDER BY ?neg` over `(-?o AS ?neg)` orders the rows, with or without LIMIT.
- **HAVING and ORDER BY compute their own aggregates for each group.**
  - `HAVING (MAX(?o) > 1)` works without MAX in the SELECT. It kept no group.
  - `ORDER BY DESC(COUNT(*))` orders the groups. It ordered nothing.
  - An aggregate in HAVING or ORDER BY makes the query group (§11.4). So `SELECT ?s … ORDER BY COUNT(*)` without
    GROUP BY is a syntax error, and `SELECT (1 AS ?x) … HAVING (COUNT(*) = 2)` gives one row for the whole result.
- **COUNT counts bound, non-error values** (§18.5.1.2). `COUNT(?x) WHERE { }` is 0, and COUNT over an OPTIONAL
  counts only the solutions that bind its variable. It counted every solution.
- **SUM and AVG have the type of their arithmetic** (§18.5.1.3–4).
  - SUM of integers is an integer: `"6"^^xsd:integer`. It was `"6"^^xsd:decimal`.
  - A float stays a float.
  - SUM of nothing is the integer 0.
  - AVG of integers is a decimal in its canonical form, `"2.0"`. It was `"2"`.
  - A simple literal `"2"` is not a number, so it makes SUM or AVG an error, and the result is unbound. It was added as
    the number 2.
- **`(expr AS ?v)` is a syntax error when `?v` is already in scope** (§18.2.4.4): in the WHERE, in GROUP BY or in the
  trailing VALUES. `SELECT (1 AS ?s) WHERE { ?s ?p ?o }` was accepted. A grouped query may project a trailing VALUES
  variable.
- **A malformed aggregate is a syntax error:**
  - two arguments, `SUM(?x, ?y)` (W3C syn-bad-06);
  - `SEPARATOR` on anything but GROUP_CONCAT;
  - no argument, `COUNT()`;
  - a missing `)`.

## Fixed

- **An aggregate's argument can be any expression** ([127]): `COUNT(?o + 1)`, `SUM(?o / 2)`, `COUNT(DISTINCT ?o + 1)`.
  These failed with "Aggregate expressions must use AS".
- **A SELECT expression can begin with an aggregate:** `(MAX(?o) - MIN(?o) AS ?span)`, `(SUM(?o) * 2 AS ?x)`.
- **GROUP_CONCAT's SEPARATOR can be a long string**, and it is read inside an expression too.
- **A grouped sub-SELECT joins its own trailing VALUES with its groups**, and projects the VALUES variables.
- **DISTINCT over grouped rows merges equal rows** when an expression uses an aggregate. That hidden aggregate was
  bound under an empty name, so DISTINCT saw a difference that was not projected.

## One path each

Each of these fixes replaced copies that had drifted apart:
- **One reader of an aggregate's argument,** `ReadAggregateArguments`. It replaces the SELECT clause's reader, the
  reader for aggregates inside an expression, and the evaluator's first-character test for a variable.
- **One substitution of a group's aggregate values,** `WithAggregateValues`. It serves the SELECT expressions,
  HAVING and ORDER BY, and replaces two copies along with their upper-cased text matchers and the `COUNT(*)`
  row-count fallback.
- **One rule for where `(expr AS ?v)` may assign.** It replaces a check that covered only a sub-SELECT's projection.
- **SUM and AVG add with the evaluator's arithmetic** (`Value.Arithmetic`). `TryParseRdfNumeric`, their own number
  reader, is deleted.

## Limits

A query computes at most 8 aggregates, and the ones in HAVING and ORDER BY count toward that limit. An aggregate that
appears in both the SELECT and HAVING is computed once. Over the limit, the query fails with "Too many aggregate
expressions (max 8)".
