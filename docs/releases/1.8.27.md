# Sky Omega 1.8.27 — Mercury: DESCRIBE, SELECT *, $x and blank nodes follow the spec

**Released:** 2026-10-28
**Version bump:** `Directory.Build.props` → 1.8.27 (with these notes)
**Predecessor:** [Sky Omega 1.8.26](1.8.26.md) — Mercury: a query's WHERE is parsed once.

## Headline

Four more parts of [ADR-055](../adrs/mercury/ADR-055-query-where-one-parse.md) and the bugs they surfaced. All were
silent wrong results, and all reached `mercury_query`, the HTTP endpoint and the CLI:
- DESCRIBE described nothing.
- `$x` and `?x` were two different variables.
- `SELECT *` listed only the variables the first rows happened to bind.
- A blank node in a pattern, such as `?s ?p _:x`, matched nothing: 0 of 5,911 triples on a live store.

## Fixed

- **DESCRIBE described nothing** (ADR-055 D3). The facade returned a SELECT row's first three values as a triple.
  DESCRIBE now returns, for each target, the triples with it as subject and then as object, each triple once:
  - constant targets (`DESCRIBE <iri>`, `ex:a`), with or without a WHERE;
  - variable targets, by the values the WHERE's solutions give them, with ORDER BY and LIMIT applied;
  - `DESCRIBE *`, the WHERE's in-scope variables.

  The `WHERE` keyword is optional, as the grammar allows.
- **`$x` and `?x` were two variables** (ADR-055 D1; SPARQL 1.1 §19.8):
  - bindings were keyed by the name with its sigil, so `$s` in one pattern did not join `?s` in another;
  - most clause parsers did not read `$` at all: FILTER, BIND, ORDER BY, GROUP BY, HAVING, MINUS, EXISTS, sub-SELECT
    projections and Update templates.

  One `VariableName` type now hashes and compares every variable name without its sigil.
- **`SELECT *` listed only the variables some row bound** (ADR-055 D7):
  - an OPTIONAL variable no row bound was missing from the header;
  - a query with no solutions had an empty header.

  It now lists the WHERE's in-scope variables (§18.2.1), then the trailing VALUES'.
- **A blank node in a pattern did not act as a variable** (§4.1.4). `?s ?p _:x` matched only a stored blank node
  labeled `_:x`, so `_:b` could not join two patterns. A labeled blank node now matches any term and joins the
  patterns that use it. It is never part of the results. Update WHERE clauses get the same fix.
- **`SELECT DISTINCT *` returned duplicate rows** when solutions differed only in a pattern's blank node, as in
  `?s <p> [ <q> ?o ]`. It now keeps the in-scope variables before DISTINCT (§18.2.5), in a query or a sub-SELECT.
- **CONSTRUCT ignored ORDER BY with LIMIT, and OFFSET.** `ORDER BY DESC(?s) LIMIT 1` returned every triple. CONSTRUCT
  now reads the same solutions a SELECT does.
- **A CONSTRUCT template's `_:b` was one blank node across all solutions**; it is now a new one per solution (§16.2).
  In `CONSTRUCT WHERE`, the pattern's `_:b` matches as a variable and the template's is fresh.
- **CONSTRUCT and DESCRIBE failed on a triple longer than 2,048 characters** with "Destination is too short". Their
  buffers now grow.
- **The BIND scope check missed VALUES and SERVICE variables.** `VALUES ?x { 1 } BIND(2 AS ?x)` was accepted.
- **A sub-`SELECT *` dropped its own trailing VALUES variable** from what it passed out.
- **HAVING didn't match a SELECT's `COUNT($s)` when written `COUNT(?s)`.**

## Changed

- One reading of the in-scope rule, `SparqlParser.AddInScopeVariables`, now serves `SELECT *`, `DESCRIBE *`, sub-SELECT
  projection and the BIND scope check. Each had its own partial version before.
- DESCRIBE's targets are read by one `DescribeTargetReader` that the parser and the executor share, the same pattern
  as VALUES.
- Stack use is unchanged: 23–39 KB across the probe shapes (`tools/probes/stack`).

## Known issues

- **DESCRIBE reads current triples from the default graph.** It does not follow AS OF or FROM NAMED.
- **A blank-node label is one variable across the whole query.** SPARQL forbids reusing a label in a second basic graph
  pattern, and Mercury does not reject that reuse.
- **A number from a VALUES clause comes back as `"7"^^xsd:integer`, while a BIND's comes back as `7`**
  ([ADR-053](../adrs/mercury/ADR-053-one-rdf-term-one-atom.md), as is `INSERT DATA`'s number form).
- **HAVING matches aggregates by their text**, separately from the SELECT's aggregate list.
- Carried over: the SPARQL 1.0 W3C manifests are not run; DISTINCT compares rows by a 32-bit hash (inferred, not
  reproduced); on Linux one debugger thread leaks per ended DrHook session; Windows lacks `RequestExit`.
