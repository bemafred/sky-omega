# Sky Omega 1.8.22 — Mercury: one pattern path for SPARQL UPDATE

**Released:** 2026-10-27
**Version bump:** `Directory.Build.props` → 1.8.22 (with these notes)
**Predecessor:** [Sky Omega 1.8.21](1.8.21.md) — DrHook: an attach waits for the target's runtime debugger.

## Headline

Through 1.8.21, the WHERE of a SPARQL Update was parsed by the old flat `GraphPattern` grammar and sent down one of
six routes chosen by counting what it contained. Some Updates lost data or deleted too much, and reported success
anyway. For example, `INSERT { … } WHERE { VALUES ?o { "a" "b" } }` reported `OK - 0 triple(s)`, and
`INSERT { … } WHERE { OPTIONAL { GRAPH <g> { … } } }` was rejected as a syntax error.

Now an Update's WHERE is parsed and evaluated exactly like a query's WHERE. It uses the pattern-tree grammar and
`TreeJoinExecutor`, and one function fills in every DELETE and INSERT template from the rows
([ADR-052](../adrs/mercury/ADR-052-update-where-one-pattern-path.md), Completed).

## Fixed

- **Updates that silently wrote nothing.** A WHERE made only of VALUES, BIND, or other non-triple patterns ran the
  templates once with no bindings, so the templates wrote 0 triples.
- **Updates that silently deleted too much or too little.** The routes chosen by counting patterns dropped FILTER,
  MINUS, UNION, NOT EXISTS, OPTIONAL, property paths and sub-SELECTs in different combinations.
- **WHERE shapes the Update parser could not read.** `OPTIONAL { GRAPH … }`, nested groups and the other group forms
  that queries accept now parse in an Update too. A syntax error anywhere in a `;`-chained request still means
  nothing runs (ADR-046).
- **WITH, USING and USING NAMED follow the spec.** USING and USING NAMED replace WITH for the WHERE. Templates still
  write to the WITH graph (or the default graph).
- **BIND results were stored without quotes.** `BIND("b" AS ?x)` stored the atom `b` instead of `"b"`. A variable's
  value now becomes a stored term through one rule, `LiteralForm.TermForBinding`.
- **Queries dropped everything after a comma object list.** In `?s :p ?a, ?b . ?s :q ?c`, the pattern-tree parser
  stopped at the comma and silently dropped the rest of the group. This also affected SELECT, ASK and CONSTRUCT.
  W3C `constructwhere03` had been passing by accident. Grammar production [79] ObjectList is now handled.
- **A missing `}` was accepted.** The pattern-tree parser now rejects an unclosed group, GRAPH block or EXISTS
  body. Before, it closed them silently.
- **FROM / USING with prefixed names.** One of `QueryExecutor`'s two copies of the dataset setup didn't expand
  prefixed graph names. Query and Update now share one `QueryExecutor.ResolveDataset`.
- **`--version` and `mercury_version` reported 1.8.16.** Since 1.8.16, version bumps changed only `<Version>`. Now
  `AssemblyVersion`, `FileVersion` and `InformationalVersion` are derived from it.

## Changed

- **`DELETE WHERE { … FILTER … }` is now a syntax error.** The spec allows only triples and GRAPH blocks in DELETE
  WHERE. Before, the FILTER was accepted.
- **text:match pre-filtering applies to Updates.** Trigram candidate lookup is now driven from the pattern tree
  (`TreeJoinExecutor.ResolveTrigramCandidates`), so an Update's WHERE gets it too.
- `UpdateExecutor` went from 1,263 to 856 lines. The six count-gated routes and their helper copies are deleted.

## Validation

- `UpdateWherePatternTests`: 31 new facade tests. Before the change, 12 of them failed. They cover:
  - the six defects in the ADR's table;
  - every group form;
  - WITH, USING and USING NAMED;
  - chained sequences;
  - syntax errors;
  - an equivalence check over 8 WHERE shapes: an Update writes exactly as many triples as `SELECT *` over the same
    WHERE returns rows.
- Mercury.Tests: 4,756 passed, 7 skipped, 0 failed, W3C conformance included. Mercury.Solid.Tests 25/25,
  SkyOmega.Bcl.Tests 12/12.
- Stack ([ADR-009](../adrs/mercury/ADR-009-stack-overflow-mitigation.md)): smallest thread stack at which an Update
  succeeds, Debug build:

  | Update | 1.8.21 | 1.8.22 |
  |---|---|---|
  | WITH + 1-triple DELETE | 833 KB | 577 KB |
  | WITH + 2-triple INSERT | 833 KB | 577 KB |
  | `DELETE WHERE { GRAPH … }` | 817 KB | 593 KB |
  | 100-triple template | 833 KB | 577 KB |
  | 9-deep OPTIONAL (parser limit 10) | could not parse | 721 KB |

- Performance: WITH + 1-triple DELETE of 10,000 matches, Release, 4 runs each. The fastest runs were 4.3 s on
  1.8.21 and 4.6 s on 1.8.22, and the runs were noisy, so there is no measured regression. We haven't measured
  where the time goes.
- Live over `mercury-mcp` 1.8.22: the `DELETE … INSERT … WHERE { OPTIONAL { GRAPH … } BIND(…) }` memory-status
  rewrite that failed on 2026-10-27 succeeded (1 triple deleted, 3 inserted). VALUES-only and BIND-only WHEREs
  wrote 3 triples, where before they wrote 0.

## Known issues

- Queries still guess where their WHERE begins. An Update now records the exact position.
- A variable's value still becomes a stored term in two places (`LiteralForm.TermForBinding` and the scan's
  `CanonicalBoundValue`). Joining them belongs to ADR-053, together with numeric literals in `INSERT DATA`, which
  are stored as bare `1`.
- A blank node in an INSERT template is reused across all solutions instead of being new for each one.
- Carried over from 1.8.21: one debugger thread leaks per ended DrHook session on Linux; Windows lacks
  `RequestExit`.
