# Sky Omega 1.8.41 — Mercury: the W3C suite cannot lose a test silently; a literal is well-formed by one rule in every format. DrHook: a session's end and a failed launch say what happened; the snapshot gives stacks and thread states

**Released:** 2026-11-11
**Version bump:** `Directory.Build.props` → 1.8.41 (with these notes)
**Predecessor:** [Sky Omega 1.8.40](1.8.40.md) — Mercury: a killed store keeps its committed writes; the MCP tool's
output parses back. DrHook: why a crashing target can disable the debugger.

## Headline

**Mercury: the W3C test data moves deliberately, and a test that stops loading fails the suite**
([ADR-059](../adrs/mercury/ADR-059-every-w3c-test-runs.md)). A Git update in Rider moved the rdf-tests submodule
past its pin. In the new data, rdf-tests #396 had removed the RDF 1.2 manifests' includes of the RDF 1.1 ones. On
that data the suite ran 1,844 W3C tests instead of 2,827, and every one of them passed. Each format now loads both
manifests. A guard test fails on any manifest that no suite loads or lists. The pin moves only in a commit that runs
the suite against the new data (D6), and a weekly workflow runs the suite against upstream's head.

**Mercury: a literal is well-formed by the same rule in N-Triples, N-Quads, Turtle and TriG.** A language tag is
well-formed BCP 47, and a base direction is `ltr` or `rtl`. `rdf:langString` and `rdf:dirLangString` are never written
as an explicit datatype, and a datatype is an IRI. Before this release each parser accepted something different, and
TriG took a blank node as a datatype.

**DrHook: what ended, and why a launch failed.** A session's end now carries the target's exit code or the signal that
ended it. A failed launch reports the step that failed, the reason and what the target wrote, and leaves no zombie. A
`DebuggerError` is handled as its documentation says. `drhook_snapshot` captures the collapsed stacks and thread
states it promised.

## Mercury: the W3C suite (ADR-059)

The submodule moved from rdf-tests `d01b141` to `202a74e`, the first update under the new rule D6. Eight upstream
commits, from 2026-11-01 to 2026-11-04:

- **#396** removed the RDF 1.2 manifests' includes of the RDF 1.1 ones. Each RDF format now loads both, from one
  table, `W3CTestContext.SuitesOf`, which the test classes and the guard both read.
- **#405** added negative syntax tests for language tags and IRIs. Nine failed: N-Quads, Turtle and TriG accepted
  `"Hello"^^rdf:langString`, `"Hello"@cantbethislong` and `"Hello"^^rdf:dirLangString`. They are fixed in the
  parsers (below).
- #401, #406 and #394 changed no result. #398, #400 and #404 change reports, the README and the Graph Store protocol
  tests, which are not loaded.

Compared test by test with `d01b141`, no test is missing. 10 are new upstream, 3 known failures pass, and 4 are new
tests of the suite itself.

**The guard** (`W3CManifestCoverageTests`, D4) reads every manifest in the two submodules: 122 at rdf-tests `202a74e`
and json-ld-api `5551473`. 78 are loaded. The other 44 are listed in `W3CTestContext.ManifestsNotLoaded`, each with
its reason. The guard fails on any of these:
- a manifest that is neither loaded nor listed;
- a listed manifest that a suite loads, or that is not in the submodules;
- an include that the manifest parser cannot read (it used to skip one silently);
- an entry it cannot make a test of, or of a kind that no test method runs.

With the loaders put back as they were, the guard named exactly the five RDF 1.1 manifests that #396 cut off.

**Tracking upstream.** `tools/check-w3c-upstream.sh` compares each pin with the head of its upstream default branch.
With `--fetch` it lists the commits between them that touch test data. With `--run` it runs the W3C suite against
upstream's head and puts the pins back. `.github/workflows/w3c-upstream.yml` runs it every Monday and fails when a
test fails against upstream. On 2026-11-11, rdf-tests upstream was at `4158bca`, past the pin: a dependabot bump of
`Gemfile.lock`, with no test data changed.

**Seven SPARQL 1.0 tests do not apply.** The guard found `sort-11` and six `sameTerm` tests in manifests that no
umbrella manifest includes. They were written for RDF 1.0, where `"xyz"` and `"xyz"^^xsd:string` are two terms, and
the queries the six `sameTerm` tests name are not in their directory. They stay unloaded, with that reason.

**Counts.** 2,653 of 2,808 W3C tests pass; 149 are known failures and 6 do not apply. The RDF formats pass 1,201 of
1,344, including all 993 RDF 1.1 tests. SPARQL passes 991 of 997, and JSON-LD 461 of 467. Known failures went from
157 to 149.

## Mercury: one rule for a literal

- **Language tags** (docs/divergence S1f). The N-Triples / N-Quads, Turtle (both of its literal paths) and TriG
  parsers check a tag with one rule, `Rdf/RdfLanguageTag.cs`: the tag must match the RFC 5646 `Language-Tag` ABNF,
  including the irregular grandfathered tags (RDF 1.2 Concepts §3.4). Before this release, N-Quads accepted ASCII
  letters, digits and hyphens of any length, Turtle any Unicode letter, and TriG any character up to a delimiter.
- **Base direction.** After `--`, the direction is `ltr` or `rtl`, matched exactly; the W3C tests reject `LTR`. 8 known
  failures pass.
- **`rdf:langString` and `rdf:dirLangString`** are never an explicit `^^` datatype, in full or prefixed form.
- **A datatype is an IRI** (S1g). TriG read the datatype with its graph-label function. So `"x"^^_:b` and `"x"^^[]`
  were accepted, and `"x"^^42` became `"x"^^`. TriG now reads every IRI through one `ParseIri`, which replaces the same
  check copied into five functions. The graph-label function is renamed from `ParseIriOrPrefixedName` to
  `ParseGraphLabel`, a name that says it also reads blank nodes. In both of its literal paths, Turtle accepted
  `"x"^^ .` with an empty datatype; all three datatype sites now reject a missing IRI.
- **Whitespace.** TriG rejected whitespace and comments before `@` or `^^` and after `^^`, such as `"x" @en` and
  `"x"^^ <dt>`. The grammar allows them, and TriG now reads them as Turtle does.

## Changed behavior: the parsers reject more

Some documents that loaded before are now parse errors: one with an ill-formed language tag (for example a subtag of
more than 8 characters), a base direction other than `ltr` or `rtl`, `^^rdf:langString`, or a datatype that is not
an IRI. A bulk load or convert stops at that line.

The rule has not been run against a Wikidata dump, because that takes hours. It is filed as
[docs/limits/language-tag-check-unrun-on-dumps.md](../limits/language-tag-check-unrun-on-dumps.md) (Latent): check a
dump before the next full load. Stores loaded before this release open and query as before; the check runs only in
the parsers.

## Fixed: DrHook

- **`DebuggerError` is handled as documented.** The callback's documentation allows nothing but `GetID` after it.
  DrHook treated it as an informational event and went on to call `Stop`, `Continue`, `Detach`, `Terminate` and
  `Release`. The session is now marked lost on mscordbi's thread, at once. Every member that would reach ICorDebug
  refuses with `DebuggerLostException`, and teardown calls and releases nothing. `StopReason.DebuggerLost` carries
  `errorHR` and `errorCode`.
- **A dead target that nobody has reaped is seen as exited.** `Process.HasExited` treats a zombie as alive, and
  finding 105's stuck PAL never reaps one. `DebugSession.TargetHasExited` asks the OS instead. On Unix it checks the
  PID and its start time, so a reused PID is not taken for the target; on Windows it uses the process handle.
- **A session's end says how the target ended.** Each end now reports `targetExit` from the OS: the exit code, or the
  signal that ended the target. Before, every exit read "ran to completion", and an exit code of 3 read the same as a
  SIGKILL. On POSIX a thread waits in `waitid(WEXITED | WNOWAIT)`, which reads the end without reaping, so mscordbi
  still reaps the child (finding 87). On Windows DrHook waits on a handle of its own.
- **A failed launch says why and leaves no process behind.** A target that exited before its runtime started used to
  wait out the 30 s timeout. It then reported only `E_FAIL`, and its zombie stayed. A launch now fails as soon as the
  target ends. The `launchFailure` it reports gives the step, the reason, and the target's pid, exit and output (at
  most 4 KiB each from stdout and stderr). The target is reaped.
- macOS reports a child held by `POSIX_SPAWN_START_SUSPENDED` as stopped to every `waitid`, so DrHook watches the
  child with `kqueue` `NOTE_EXIT` instead.
- On POSIX, DrHook now looks up the program itself, with `execvp`'s rules and `access(X_OK)`, before anything is
  spawned. So a missing program fails at the lookup step with the OS's error on macOS and Linux alike, not as the
  failure of the Linux hold shell.
- **The snapshot.**
  - `drhook_snapshot` captures each thread's managed stack, named from the method rundown, and gives each thread a
    state.
  - The JSON collapses stacks across threads, so a pool of idle threads is one entry.
  - The runtime provider was enabled at Warning level, so the GC and contention counts were always zero. It is now
    enabled at Informational.
  - HOTSPOT uses the samples in which a thread ran managed code. Before, it used each thread's share of all samples,
    which only measures how many threads there are.
  - A thread's `at` is the innermost frame in at least 80% of its samples.
  - `threadCount` is now `sampledThreads`, and says which threads it never lists.
  - The JSON is written without reflection, so it works in trimmed, AOT and file-based hosts.
  - The capture is bounded: 64 MiB of trace and 64 frames per stack.
- **Every tool result is written unescaped.** Only the snapshot used relaxed escaping. Every other result escaped
  `+ < > & ' "` as `\u` sequences that the LLM operator had to decode. All of them now use one `OperatorJson.Options`.

## DrHook: research (ADR-016, ADR-017)

- **ADR-016 Step 4.** Findings 104 and 105 were measured on Linux x64 (zbook), with stacks named from Microsoft's
  symbol files, and on the six CI runners.
  - Ending the session at a crash's stop was clean in 239 of 239 runs.
  - Continued crashes hung the debugger on the four macOS and Linux runners (40 of 160 runs) and on neither Windows
    runner (0 of 80).
  - A launched target hangs the debugger as an attached one does, and a missing `ProcessExited` marks the stuck
    session in both cases.
- **ADR-016 Step 5.** Probe 106 tests the debugger running in a worker process. It is smoke-tested on omega, not yet
  at scale.
- **[Finding 107](../../poc/drhook-engine/findings/107-diagnostics-port-hold-is-inherited.md).** The runtime's diagnostics-port pause holds a target before its first managed code, but every .NET
  child inherits the pause and waits for a listener. So the Linux launch keeps its shell.
- **ADR-017, debugging a process tree from one session.** Proposed and accepted on 2026-11-08.
  - Step 2 ([finding 108](../../poc/drhook-engine/findings/108-rider-holds-children-with-the-diagnostics-port.md)):
    Rider catches child processes with that same pause and a backend listener.
  - Step 3 ([finding 109](../../poc/drhook-engine/findings/109-diagnostics-port-pause-on-every-platform.md)): the
    pause holds and spreads to children on Linux, macOS and Windows.
