# Sky Omega 1.8.39 — Mercury: parsers read short reads and a byte order mark; one literal split; one writer per results format

**Released:** 2026-10-30
**Version bump:** `Directory.Build.props` → 1.8.39 (with these notes)
**Predecessor:** [Sky Omega 1.8.38](1.8.38.md) — Mercury: written text has no byte order mark; the pruning audit log is
N-Quads.

## Headline

**Every RDF parser now reads a stream whose reads return fewer bytes than asked, and a document that starts with a
byte order mark.** Network bodies, pipes and decompressors return short reads. On one, the RDF/XML parser looped
forever at 100% CPU, and the TriG and N3 Patch parsers failed. TriG, RDF/XML and Solid's N3 Patch now read through
one reading layer, `Utf8DocumentReader`, instead of three more copies of Turtle's.

**A Solid PATCH body could hold a server thread forever.** An N3 Patch body starting with `%` or a non-breaking space
made the parser loop. It is now a 400. A patch written as the Solid specification writes it, with `a` for
`rdf:type`, parsed as empty and did nothing; it now applies.

**SPARQL results are written by one writer per format.** The HTTP endpoint and the SPARQL tool each had their own
JSON, XML, CSV and TSV writers, each with its own bugs. CSV wrote `x` as `"""x"""`; CONSTRUCT asked for as JSON-LD
came back as N-Triples labelled `application/ld+json`.

## Fixed: a byte order mark at the start of a document

N-Triples, N-Quads, Turtle, TriG and JSON-LD rejected a document starting with a UTF-8 byte order mark ("got
U+FEFF"). `Utf8ByteOrderMark` holds the rule: a reader skips one at the start of a document and nowhere else. All
eight readers follow it, the six RDF parsers, N3 Patch and SPARQL JSON results. A stream whose first read returns
fewer than three bytes is read the same way. A byte order mark after the start is still an error.

## Fixed: short reads and UTF-8

`Utf8DocumentReader` (src/Mercury/Rdf) is the Turtle parser's self-refilling lookahead (1.7.4) with the N-Quads
parser's UTF-8 validation. Its lookahead reads until it holds the bytes it needs, invalid UTF-8 is an error, and a
lookahead past the buffer is an error rather than a silent stop.

- **TriG** returned end of input when its buffer was empty, so a stream returning one byte per read failed at once
  ("Unknown directive"), and a multi-byte character split by a read was decoded as its first byte.
- **RDF/XML** looped forever on such a stream. Its name readers also appended each byte as a character, so
  `<e:éléphant rdf:resource="..."/>` gave the predicate `<http://example.org/Ã>` and the rest of its start tag as a
  literal.
- **N3 Patch** read each byte as a character, so `café` became `cafÃ©`, and it refilled only between statements, so
  a body arriving in short reads was cut short.

Each parser's own buffer layer is deleted. Turtle and N-Quads keep theirs, which were already correct.

## Fixed: N3 Patch

- A body whose next character starts no term, such as `%` or U+00A0, looped forever. It is "Unexpected character
  U+XXXX", which the PATCH handler returns as 400.
- At the top level, `a` was read as a prefixed name, so `_:rename a solid:InsertDeletePatch` was never found and the
  patch did nothing.
- An IRI or literal cut off by the end of input was returned as read so far. It is "Unterminated IRI" or
  "Unterminated literal".

## Fixed: RDF/XML has one root element

The document loop consumed any character outside markup, so `xyz<rdf:RDF/>`, text after the root, a second root
element, a stray end tag and a CDATA section outside the root all loaded. XML 1.0 [1] allows one root element, with
only comments, processing instructions, a document type declaration before the root, and whitespace around them. Each
of the others is now a parse error naming what it found.

**Documents that loaded before may now fail:** an RDF/XML file with text or a second element outside its root.

## Fixed: one split of a stored literal

A stored literal's lexical form is decoded (ADR-044), so it may hold `"`, and its closing quote is the last `"`.
Fourteen places split literals. Nine used the last quote, and five used a forward scan that skips `\"`, which stops
at an internal quote. `StoredLiteral` is the one split now.

- **RDF/XML output** cut a literal at its first internal quote, and turned a backslash followed by `n` into a line
  break. This was in every RDF/XML output, CONSTRUCT results and convert included. A carriage return is now written
  as `&#xD;`, since XML reads a raw one as a line feed.
- **The full-text index** indexed a literal only up to its first internal quote, so `text:match` missed words after
  it.

## Fixed: SPARQL results

`SparqlJsonResultWriter`, `SparqlXmlResultWriter` and `SparqlCsvResultWriter` are the one implementation. The HTTP
endpoint and the SPARQL tool write through them, and their own writers are deleted.

- **CSV** writes a literal as its lexical form, with quotes doubled (it wrote `x` as `"""x"""`).
- **TSV** writes a literal in Turtle syntax, so an internal quote is escaped.
- **JSON** escapes every control character as `\uXXXX`; another control character made the document invalid.
- **XML** writes a carriage return as `&#xD;`.

## Fixed: CONSTRUCT and Solid GET write every format they name

A CONSTRUCT or DESCRIBE result asked for as JSON-LD came back as N-Triples labelled `application/ld+json`. The HTTP
endpoint, the SPARQL tool and Solid's resource and container GET each had a switch that fell back to N-Triples. They
all write through `RdfDocumentWriter` now, the one map from a format to its writer, for N-Triples, N-Quads, Turtle,
TriG, RDF/XML and JSON-LD.

Solid's container GET wrote its type triples with bare IRIs, so its default Turtle was not Turtle; it is valid now.
`mercury-sparql --rdf-format` and the REPL's `.rdf-format` accept all six format names.

## Changed output

- The endpoint's JSON results are indented (the same data).
- CSV and TSV lines end with LF on every platform, as in the W3C test results.
- Solid's Turtle writes IRIs in full, without the three standard `@prefix` lines.

## Benchmarks: the bzip2 measurements

A bzip2 speed comparison in the test suite failed on a loaded CI runner. It and three measurement classes that read a
file in `/tmp`, and otherwise reported passed, are BenchmarkDotNet benchmarks now. `BZip2LargeFixture` generates a
50 MB Wikidata-shaped N-Triples document and compresses it with the `bzip2` tool.

On omega, `--job short`:

| Path | Single-threaded | 4 workers | 14 workers |
|------|----------------:|----------:|-----------:|
| Decompress 50 MB | 452 ms | 130 ms | 53 ms |
| Convert (bzip2 → Turtle → N-Triples) | 743 ms | 283 ms | — |

Converting the decompressed text takes 260 ms, so on the convert path the parallel stream removes nearly all of
decompression's cost. A block decodes 1.16 times slower at 14 workers than at one. See
[compression.md](../architecture/technical/compression.md).

## Fixed: the attach-pipe test hung on Windows

`PipeClient_Command_IsTheFirstBytesOnThePipe`, new in 1.8.38, hung both Windows CI jobs until their 90-minute
limit. A Windows named pipe with no buffer completes a write only when the other end has read all of it, and the test
answered before reading the whole command line. It reads the line first now, under a 30-second limit. The production
server reads whole lines and was not affected.

## Known, not fixed

- RDF/XML reads an undefined entity reference such as `&foo;` as `?`, accepts an empty document, and does not check
  the name of the end tag that closes `rdf:RDF`.
- N3 Patch keeps a literal's escapes as written and ignores `@base`.
