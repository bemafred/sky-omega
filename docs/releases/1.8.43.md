# Sky Omega 1.8.43 — DrHook: a view shows the target's state as it is now, to the end. Mercury: a store has one clock; a write is decided once

**Released:** 2026-11-14
**Version bump:** `Directory.Build.props` → 1.8.43 (with these notes)
**Predecessor:** [Sky Omega 1.8.42](1.8.42.md) — DrHook: the views are tools that wait for a session and show it from
its start. Mercury: `NOW()` is one value per query; date arithmetic.

## Headline

**DrHook: the dashboard says what the target is doing now.** Until this release a view was told the target's state
at stops only. It kept showing the last stop while the target ran and after it exited. A view is now told when the
target runs and how it ended, and the dashboard's two crowded panes show what a human looks for: the hypotheses stay
on screen, and the console pane shows the target's lines. These are the two flaws the 1.8.42 notes listed as known.

**Mercury: the first two steps of [ADR-061](../adrs/mercury/ADR-061-a-facts-own-times.md)**, which Martin accepted on
2026-11-14. A store has one clock, and a write on a Cognitive store is decided once, from what the store holds for the
quad. The Mercury part of these notes is written from the commits of the sky-omega instance (`b8647c86`, `e6a234a5`,
`33e7701c`).

## DrHook: the state a view shows

| When | The dashboard's title | Before |
| --- | --- | --- |
| At a stop | `Stopped: Breakpoint` | the same |
| A resumed target has run for 250 ms | `Running` | the stop it had left |
| The target exited | `target exited with code 3` | the last stop |
| The target was killed | `target was killed by signal 11 (SIGSEGV)` | the last stop |
| The debugger was lost | `debugger lost` | the last stop |
| The session was ended at a stop | `last: Stopped: Breakpoint` | `Stopped: Breakpoint` |

- **A snapshot is published when the target runs.** `drhook_continue` and the step tools publish one when the target
  has not stopped again within 250 ms, and `drhook_continue` with `waitForBreakpoint=false` publishes one at once. A
  step that completes sooner publishes only its stop, so the panes are not emptied between two steps.
- **A last snapshot is published when the target exits or the debugger is lost.** It says how the target ended:
  the wire's `session` object gained an optional `exit` field (`exited with code 3`). The stack pane shows it in
  place of the frames, and `drhook-viz-console` prints it in its snapshot block.
- **The server sends what was published before it stops.** `DebugStateServer.Stop` dropped the messages its
  publisher had not yet taken, so the last output of a session and its last snapshot could be lost. The publisher now
  makes one more pass, for at most the send timeout (2 s). A view that does not read cannot hold the stop longer than
  that.
- **A session ended at a stop keeps that stop on screen, marked as the last.** After `drhook_stop`, `drhook_detach`
  or `drhook_kill` the target is not stopped there any more, and the title says `last:`. The reason given to the tool
  is emitted as a hypothesis, so it is the braid's last line.

A view built against 1.8.42 ignores `exit`. A 1.8.43 view reads a 1.8.42 server's lines, and shows what that server
sends.

## DrHook: the dashboard's braid and console panes

- **Braid:** the lifecycle events between two hypotheses or log lines are one entry, each name once with its count:
  `Δ event      LoadAssembly ×8  LoadModule ×8  NameChange  CreateThread`. The 18 events of a launch took 18 rows
  of a six-row pane; they take one. The entry wraps when the pane is narrow.
- **Console:** the pane shows the target's output as lines, each led by its stream (`[stdout]`, `[stderr]`). The
  stream delivers what each read of the pipe returned, which is not line-aligned; the pane printed those chunks, with
  an empty row after each and no label on a chunk's second line.

`drhook-viz-console` is unchanged in both: it prints every delta in order, and console output as it arrives.

## Mercury: ADR-061 is Accepted, and its first two steps are built

- **ADR-061 is Accepted** (`b8647c86`) for the model, the words and their rules, and the guarantees. The stored
  layout is not covered. Its plan is ten steps, P0 to P9.
- **A store has one clock (P0, `e6a234a5`).** `StorageOptions.Clock` is a `TimeProvider`, the system clock unless one
  is given. Every memorized and forgotten time is a reading of it taken under the write lock, and `NOW()`, "now" in a
  current read and the listing of graphs read the same clock. The single-write path read the clock twice, once before
  the lock; it reads once, under it.
- **A write on a Cognitive store is decided once (P1, `33e7701c`).** Inside one clock reading only the last operation
  on a quad counts. What a caller can see:
  - A fact memorized and forgotten inside one clock reading leaves no entry. It left one with equal times.
  - A fact forgotten and memorized again inside one reading keeps its period unbroken. A batch that added, deleted
    and added a new quad left it forgotten.
  - A fact told again while it is remembered adds no entry to any index.
  - Memorizing a remembered quad and forgetting one that is not remembered change nothing.
  - An update counts a quad when it changes whether the quad is remembered: `INSERT DATA` of remembered facts reports
    0. `AddCurrent` and `AddCurrentBatched` return whether the fact became remembered; they returned nothing.
- **The log holds the decided change.** Four new log records begin, end, remove and continue a period (operation
  codes 6 to 9). Add with a stated time, Retract, and logs written before this release keep the old records until a
  later step.

The words ADR-061 decides (`MEMORIZED`, `FORGOTTEN`, `SINCE`, `BEFORE`, `INCLUDING FORGOTTEN`) are still not built.

**Before 1.8.43 opens a live store, and before you go back to 1.8.42:** a write to a Cognitive store puts records
with operations 6 to 9 in `wal.log`. A build before this release that opens a log still holding one refuses to open
and keeps the log (ADR-054 D8, "operation N, which this Mercury does not know"). After a clean close the log holds
only its checkpoint record, and an older build opens the store. This is read from the code by the sky-omega instance;
it was not run across the two versions. 1.8.43 has not run on a copy of a live memory store. On zbook the Mercury
tools stay at 1.8.42 for this reason; the DrHook tools are 1.8.43.

## Known, not fixed

- **Two Mercury tests fail on zbook, in 5 of 6 runs.** `QueryEvolution_DeletedTriple_IsVisibleWithClosedInterval` and
  `QueryEvolution_MixedDeletedAndActive_ShowsAll` add a fact and delete it at once, and expect the ended period in
  the fact's history. The store compares clock readings in milliseconds, and by the write rule a fact memorized and
  forgotten inside one reading leaves no entry. On zbook the two writes fall in the same millisecond. They passed on
  omega and in CI run 43587258551 on all six platforms, where the writes took longer. The tests depend on timing; the
  rule behaves as ADR-061 states it. Reported to the sky-omega instance, not changed here.

- A target that exits while no tool call waits for it (after `drhook_continue` with `waitForBreakpoint=false`) is
  shown as `Running` until the next tool call.
- `drhook-viz-console` prints console output as the chunks arrive, with an empty line after each.
- The views were not run on Windows or macOS in this release. CI runs their tests on all six platforms.
- A target that dies during a mscordbi request still leaves the DrHook debugger unusable in its process, until the
  MCP server restarts (finding 105). The worker process (ADR-016 Step 5) is not built yet.
