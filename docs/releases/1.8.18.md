# Sky Omega 1.8.18 — Mercury on Windows: presized files are sparse; first Windows arm64 run

**Released:** 2026-10-26
**Version bump:** `Directory.Build.props` → 1.8.18 (with these notes)
**Predecessor:** [Sky Omega 1.8.17](1.8.17.md) — Mercury's store pool reports its state; first Linux arm64 run.

## Headline

On omega-windows, a Parallels VM running Windows 11 on arm64 (4 cores, 8 GB, NTFS with 205 GB free), 57
Mercury.Tests failed with "There is not enough space on the disk". It was a Mercury bug, and it would have hit any
Windows user of bulk mode.

Mercury sizes its memory-mapped files ahead of use: a bulk-mode Reference index starts at 1 TB, a Temporal or
Versioned index at 256 GB, and even a default store presizes about 5.6 GB across its files. On macOS and Linux an
extended file is sparse by itself, so the unwritten length costs no disk. NTFS reserves the whole length unless the
file is marked sparse first, and Mercury never marked it. The code's comments assumed NTFS behaved like APFS; that
assumption had never been checked.

Measured on the VM before the fix: a plain 300 GB file failed with the same error the tests hit, and a plain 8 GB
file took 8 GB of free space. Marked sparse, files of 300 GB and 1 TB took 0 bytes, and a full-length mapped view with
writes at both ends worked. During a full test run, free space on C: fell from 205 GB to 24.5 GB; with the fix, its
lowest point was 182.3 GB.

It was also the first run of the whole suite on Windows. Apart from Mercury's 57, the only failures were 12 DrHook
integration tests that start `/bin/bash`, which is the next step of
[ADR-007](../adrs/drhook/ADR-007-teardown-concurrency-test-debug.md) Phase 9.

## Added

- **`SparseFile.SetLength(FileStream, long)`** in `Mercury.Runtime`: sets a file's length, marking the file sparse
  first on Windows (`FSCTL_SET_SPARSE`). The attribute stays with the file, so later growth stays sparse, and a store
  created by an earlier version becomes sparse from its next growth on. On a filesystem without sparse support
  (FAT32, exFAT, some network shares) the length is still set and fully reserved, so a shortage surfaces as that
  filesystem's own disk-full error.

## Fixed

- **Presized storage files reserved their full length on Windows.** Every place Mercury sizes or grows a mapped file
  now uses `SparseFile.SetLength`: `BTreeFile` (all four index types), `HashAtomStore` (data, hash index, offsets
  and the rehash file) and `TrigramIndex` (hash and postings). `MphfTranslationTable` keeps a plain `SetLength`,
  since it writes the whole file straight away.
- **`TextMatch_TrigramPreFiltering_ReducesEvaluations` never deleted its store.** The next run's stale-directory
  cleanup removed it, but until then it held 5.6 GB on Windows.

## Changed

- **DrHook tests that silently returned on Windows now report as skipped**, each with its reason (xunit
  `Assert.SkipWhen`, MSTest `Assert.Inconclusive`). A silent `return` counted as a pass for behaviour that was never
  checked.
- Comments in `HashAtomStore` and `TemporalQuadIndex` no longer claim NTFS is sparse by itself.

## Validation

- **omega-windows (Windows 11 arm64):** full `dotnet test`: 5,010 total, 4,985 passed, 13 skipped, 12 failed (all the
  DrHook `/bin/bash` spawn, above). Mercury.Tests passed, including the new `SparseFileTests`, which create a 1 TB file
  on the VM's smaller disk.
- **omega (macOS, M5):** Mercury.Tests 4,725 passed, 0 failed, 7 skipped (the 1 TB test skips on a disk with more than
  1 TB free); DrHook.Engine.Tests 174/174.

## Known issues

- **DrHook integration tests cannot spawn their targets on Windows.** `TargetSpawn` runs every target under
  `/bin/bash` to give it its own process group (findings 87 and 90), a POSIX mechanism. A Windows path, with a Job
  Object in place of the process group, is the next step of ADR-007 Phase 9.
- Carried over from 1.8.17: `dotnet test` does not show xunit's diagnostic messages; `dotnet test` exits 0 when its
  front end gets SIGTERM; NCrunch is unverified with xunit.v3.
