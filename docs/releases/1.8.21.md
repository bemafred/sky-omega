# Sky Omega 1.8.21 — DrHook: an attach waits for the target's runtime debugger

**Released:** 2026-10-27
**Version bump:** `Directory.Build.props` → 1.8.21 (with these notes)
**Predecessor:** [Sky Omega 1.8.20](1.8.20.md) — DrHook: a Windows debuggee's console is isolated; a Linux host crash fixed.

## Headline

On Linux and macOS, attaching to a .NET process in the first milliseconds of its startup could kill the debugger
host with SIGSEGV. On omega-ubuntu (Linux arm64) that was about 1 run in 40 of the VSTest attach tests, the second
host crash that 1.8.20's notes left open ([finding 99](../../poc/drhook-engine/findings/99-attach-before-debugger-started-segv.md)).
DrHook now waits until the target's runtime has started its debugger before it attaches.

## Fixed

- **An attach during the target's runtime startup could crash the debugger host (Linux, macOS).** This is a defect
  in the runtime's debugger library (mscordbi):
  - On these platforms it queues its managed attach unconditionally.
  - If the attach connects after the target has created its debug transport but before its runtime has marked its
    debugger initialized, mscordbi opens no IPC channel. The queued attach then dereferences that channel on
    mscordbi's own thread.

  `DebugSession.Attach` and `AttachAndOwn` now wait, for up to 10 s, until the target has its `.NET Debugger`
  thread. The runtime starts that thread right after the mark. A target that doesn't get there in time (still
  starting, or debugging disabled with `DOTNET_EnableDiagnostics=0`) is refused with `CORDBG_E_TIMEOUT` and a message
  that says why. Windows queues the attach only when it is safe, so there's no wait there; launch is unaffected.
- **`ConcurrentPauseStopTest` synced on the clock.** It paused 100 ms after attaching, which on a slow or loaded
  machine could be before the target's exception flood began. Under VSTest, Dispose then landed mid-handshake and
  `dotnet test` missed its 10 s exit. It now runs to a breakpoint inside the flood first, as findings 94 and 95 did
  for the other flood tests.
- **`WindowsSpawnTests` asserted a scheduler state.** A thread created suspended reads `Ready` until it is first
  scheduled. The test now checks that the child doesn't run before it is resumed.

## Added

- `Interop/TargetThreads.cs`: reads a target's thread names (`/proc/<pid>/task/*/comm` on Linux, `proc_pidinfo` on
  macOS), with `TargetThreadsTests`.
- Probe 66 (`66-early-attach-smoke.cs`). With gdb in non-stop mode, it holds only the target's startup thread at
  the instruction that marks the debugger initialized, so the attach lands in exactly that state:

  | | held | released 2 s in |
  |---|---|---|
  | without the guard | 3/3 host SIGSEGV | 3/3 host SIGSEGV |
  | with the guard | 3/3 refused | 3/3 stopped |

## Validation

- omega-ubuntu (Linux arm64), the six VSTest attach tests in a loop:
  - Before: 1 host crash in 40 runs.
  - After: 0 in 80 runs, the last 40 with no failure at all.
  - Full integration suite: 18 passed / 1 skipped, 6 of 6 runs.
- omega (macOS): DrHook.Engine.Tests 186 passed / 1 skipped; integration 18 / 1 in 3 of 3 runs.
- elite (Linux x64): unit 186 / 1; integration 18 / 1 in 3 of 3.
- omega-windows (Windows arm64): unit 179 / 8 skipped in 5 of 5 runs; integration 17 / 2 in 3 of 3.

## Known issues

- **One debugger thread leaks per ended session on Linux.**
  - A target killed with SIGKILL leaves its `clr-debug-pipe-*` FIFOs behind.
  - mscordbi's transport worker for that session then blocks forever opening one of them.
  - A host that has run many sessions holds one such thread per session.
- Windows still lacks `RequestExit` (graceful stop). The probe corpus and `drhook-mcp` have not run on Windows yet,
  and nothing has run on Windows x64 ([ADR-007](../adrs/drhook/ADR-007-teardown-concurrency-test-debug.md) Phase 9).
- Carried over: `dotnet test` does not show xunit's diagnostic messages; `dotnet test` exits 0 when its front end gets
  SIGTERM; NCrunch is unverified with xunit.v3.
