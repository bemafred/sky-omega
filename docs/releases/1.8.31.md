# Sky Omega 1.8.31 — Mercury: syntax by the grammar, FROM as one merged graph, property paths by §18.6

**Released:** 2026-10-29
**Version bump:** `Directory.Build.props` → 1.8.31 (with these notes)
**Predecessor:** [Sky Omega 1.8.30](1.8.30.md) — Mercury: MIN and MAX order as ORDER BY does.

## Headline

**The SPARQL 1.0 triage continues: 22 known failures remain, from 56 at 1.8.29.**
- The parser now follows the grammar for a group's `.` separators, predicates, GRAPH names, blank-node labels,
  prefixed names and string literals. Queries it used to accept and guess at are now syntax errors.
- One reader handles property lists, and one handles prefixed names. Before, there were two property-list readers and
  four prefixed-name readers, and they had drifted apart.

**A FROM dataset's default graph is one graph, the RDF merge of the FROM graphs (§13.2).**
- Before, the FROM graphs were scanned one after another. A triple in two of them matched twice, and a property path
  stopped at the edge of a graph.
- Now a path walks the merge: with `a -r-> b` in g1 and `b -r-> c` in g2, `<a> <r>+ ?o` under `FROM g1 FROM g2` finds
  both `b` and `c`.

**Property paths follow §18.6 with both ends unbound.**
- An alternative `P|Q` is a UNION, and `^(P)` is `P` with its ends swapped. Both are translated when the query is
  parsed, as sequences already were.
- `p?` and `(P)?` have one evaluation. Each start node is paired with itself and with what one step of the path
  reaches.

**The W3C suites are pinned at upstream main.** This took in 50 upstream commits. All 26 new failures are triaged:
- the harness was fixed for 9 of them;
- 2 are fixed in this release;
- the rest are known failures, each listed with its cause.

## Changed: what queries return

These changes in behavior follow SPARQL. Each was wrong before.

- **Invalid syntax is an error.**
  - A missing, leading or doubled `.` in a group is an error ([54], [55]).
  - A blank node or literal used as a predicate ([78]) or as a GRAPH name ([58]) is an error.
  - A blank-node label used in two basic graph patterns of one WHERE is an error (§19.6). A FILTER doesn't end a basic
    graph pattern; any other clause does.
  - In a blank-node property list, `[,]`, `[;]` and a `.` inside `[ ... ]` are errors. So is `[]` alone as a triple.
- **FROM NAMED with no FROM gives an empty default graph.** A dataset clause describes the whole dataset, so the
  store's default graph is no longer read. USING NAMED with no USING behaves the same way.
- **The graph lists are sets.** A graph named twice in FROM or FROM NAMED no longer returns every solution twice.
- **A triple in two FROM graphs is in the default graph once**: in a plain match, a join, ORDER BY with LIMIT, and
  COUNT.
- **An alternative keeps the Union's duplicates** (§18.6). `<a> <x>|<x> ?o` returns `m` twice. Before, it did this
  only when both ends were unbound; with one end bound it returned `m` once.
- **ORDER BY orders IRIs by their text.** IRIs were compared with their angle brackets, so `<…/s1>` sorted before
  `<…/s>`. MIN and MAX use the same comparer and are fixed with it.

## Fixed

### Property paths

- **Every path works inside `[ ... ]`.** The old blank-node reader kept only a path's base IRI, so every path except a
  sequence matched nothing there. Brackets now find their closer with the token rule, so a bracket inside a literal or
  IRI doesn't close them.
- **Two sequences in one pattern match.** The executor used to expand a sequence when the query ran, numbering its
  middle nodes from 0 each time. Two sequences in one pattern, or a sequence beside `[ ... ]`, shared a middle node and
  matched nothing. Now a sequence becomes one triple per step when the query is parsed.
- **Paths with both ends unbound:**
  - `?s (x/y)|p ?o` failed with "Undefined prefix '(<urn:'".
  - `?s p? ?o`, `?s (P)? ?o` and `?s ^p? ?o` missed the zero-length matches, or returned a row with one end unbound.
  - `?s ^(P) ?o` returned a row with one end unbound.
- **A bound object end of `(P)?` is walked backward.** It was walked forward.
- **A value bound to a variable matches itself only when it is a node of the graph** (§9.3). A constant always does.
- **The parse depth limit:**
  - Only a sequence takes a level of the limit, so a triple ten blank-node lists deep is within it.
  - An alternative of twelve branches is one UNION, not twelve nested ones, so it fits too.
- **Paths cross FROM graphs**, including `*` and inverse paths.

### Names and literals

- **Prefixed names follow [140] and [169].** This covers the grammar's Unicode name characters, dots inside a prefix
  or local name, an empty local name, and a checked percent escape. `:a\-b` expands to `<…a-b>`.
- **FILTER accepts a function with the empty prefix.**
- **A long string can hold an escaped quote.** Patterns read literals with the token rule's string reader.
- **A language tag keeps its digit subtags.**

### EXPLAIN

- EXPLAIN draws a sequence step by step. It names a join variable as `?#j0`, and an `rdf:` IRI where it used to draw
  `?` (ADR-055 D6, revised).

## Stack

Measured with `tools/probes/stack` on arm64.
- The FROM merge first made `ExecuteTemporalQuery`'s frame larger, from 1,104 to 2,384 bytes, and raised nest5's
  smallest completing stack from 23 to 39 KB.
- Translating the paths at parse then shrank the scan. `TriplePatternScan.Initialize` went from 5,920 to 2,000 bytes,
  and `MoveNext` from 5,168 to 1,392.
- Every query shape now completes in 23 KB. That includes nest5, complex and nest10, which needed 39 KB before.

The only remaining cost: `p?` creates a string for each node it reaches, where it used to bind straight from the
index.

## Tests and conformance

- **W3C submodules:** rdf-tests moved from `f172950` to `d01b141`, and json-ld-api to `5551473`. Run
  `./tools/update-submodules.sh` after pulling.
- **The harness respects a query's own dataset.** Before, it added FROM NAMED for each `qt:graphData` even when the
  query described its own dataset. Now that FROM NAMED alone means an empty default graph, the harness also adds FROM
  for the test's default data.
- **The RDF format suites check the known-failure list, not the skip list.** The skip list's `nfc` pattern matched six
  of their passing tests.
- **36 known failures remain, each with its cause in `W3CTestContext.KnownFailures`:**
  - 22 in SPARQL 1.0: BASE resolution, long string and numeric literal forms in a pattern, the ADR-053 term-identity
    cases, REGEX escapes, and three malformed expressions that ADR-057 covers;
  - 5 in SPARQL 1.1: a trailing VALUES is not joined after GROUP BY and before the SELECT expressions (§18.2.4.1);
  - 2 in RDF/XML: an XMLLiteral keeps unused namespace declarations;
  - 7 in Turtle and TriG: the characters an IRIREF excludes are checked only when written raw, and `{` `}` not at all.
- New tests: `PathEndsUnboundTests`, more `GraphDatasetTests` cases (merge, duplicates, paths across graphs), and
  `ExpressionTermTests.OrderBy_Iris_OrdersByTheirText`.
- Full suite: 6,044 tests, 0 failed, 45 skipped.

## ADRs

- [ADR-057](../adrs/mercury/ADR-057-expression-read-once.md) is **Proposed**: an expression is read once.
  - Today the parser only finds where an expression ends. The evaluator then reads the text again for every row, with
    a lexer of its own.
  - A probe showed 12 of 14 malformed expressions parse, and three of them return answers.
  - Q1–Q4 are open.
