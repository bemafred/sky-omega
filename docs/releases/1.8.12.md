# Sky Omega 1.8.12 — Mercury: every operation of a chained update runs

**Released:** 2026-10-25
**Version bump:** `Directory.Build.props` → 1.8.12 (`db40f79`)
**Predecessor:** [Sky Omega 1.8.11](1.8.11.md) — DrHook: the braid, cooperation-free visual capture, and the production pass.

## Headline

A SPARQL update request can hold several operations separated by `;`. Through 1.8.11, Mercury ran only the first and dropped the rest without any error. `DELETE DATA {…} ; INSERT DATA {…}` deleted and never inserted. Every production surface was affected: MCP, HTTP, the CLI and the REPL. From 1.8.12, every operation runs, in order.

This was [ADR-046](../adrs/mercury/ADR-046-multi-operation-update-facade.md), Accepted in June but never implemented. It came back on 2026-10-24 while we bootstrapped Mercury on a new Ubuntu LTS machine. That was the second time it lost writes on Lucy's main memory-write path.

**If you run an older version:** send one operation per request until you upgrade.

## Fixed

- **Chained updates run in full.** `SparqlEngine.Update` now uses `ParseUpdateSequence` and `UpdateExecutor.ExecuteSequence`. These are the parser and executor the W3C suite already tested; the facade just never called them. The whole request parses before any of it runs, so a syntax error in any operation means nothing executes.
- **A missing `;` is an error, not a drop.** `INSERT DATA {…} INSERT DATA {…}` used to run the first operation and discard the second. It is now a parse error: `Expected ';' or end of update request at position N`.
- **`LOAD SILENT` is silent.** SILENT suppressed only thrown errors. A reported failure, such as file not found or a size or triple limit, still failed the operation. It now suppresses both kinds.

## How failures behave

Operations run in order, and each one is saved on its own. If an operation fails, and it isn't marked SILENT, the operations after it don't run. The ones before it keep their effects. The error names the failing operation:

```
Update operation 2 of 3 failed; operations after it were not run: File not found: …
```

That meets what the SPARQL 1.1 spec requires: the same effects as running the operations one by one, and a failure stops the rest. All-or-nothing, which the spec only recommends, is not offered; ADR-046 explains why.

## Docs: bootstrap into a named graph

The documented bootstrap `LOAD` had no target graph, so the 71 bootstrap triples landed in the default graph. Recall only queries the `GRAPH ?g { … }` union, so a freshly bootstrapped store recalled nothing. All bootstrap instructions now use `INTO GRAPH <urn:sky-omega:bootstrap>` (`37f1be1`). To repair a store that was already bootstrapped into the default graph:

```sparql
MOVE DEFAULT TO <urn:sky-omega:bootstrap>
```

## Validation

- **New tests:** 10 tests on `SparqlEngine.Update`, the entry point production uses, plus 1 on the REPL. They cover the original repro in a named graph, a prefix declared between operations, a `;` inside a literal, abort and SILENT behaviour, a late syntax error, a missing separator and an empty request. All 11 failed before the fix.
- **Suites:** Mercury.Tests 4722 passed, 0 failed, 6 skipped (the 6 depend on the test environment), with the W3C suites green. Mercury.Solid.Tests 25/25. The solution builds with 0 warnings.
- **Live runs:** the repro through the `mercury` CLI reported "3 triples affected", and both writes landed. Over MCP, `mercury-mcp 1.8.12` applied a chained `DELETE … ; INSERT …` memory update in one request.

## Known behaviour

Both REPLs (`mercury` and `mercury-sparql`) run a statement as soon as a line ends with `;`. A request typed across several lines, with `;` at the line ends, therefore runs as several separate requests. Nothing is lost, but they don't form one request. Type a chained request on one line to send it as one.
