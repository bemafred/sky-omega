# Sky Omega 1.8.25 — Mercury: no silent drops, LIMIT 0, one route for every WHERE

**Released:** 2026-10-27
**Version bump:** `Directory.Build.props` → 1.8.25 (with these notes)
**Predecessor:** [Sky Omega 1.8.24](1.8.24.md) — Mercury: every result row keeps its own column names.

## Headline

A Mercury MCP memory write stored 8 of its 25 triples and reported success. An Update template was parsed into
fixed-capacity structs that silently kept at most 8 triples per `GRAPH` block, 4 `GRAPH` blocks and 32 default-graph
triples. Templates now hold every triple they are written with.

The same release fixes `LIMIT 0` (it returned every row) and DISTINCT with GROUP BY (it changed the counts). A WHERE
without triple patterns now evaluates through the same tree as every other WHERE. Each fix replaced copies of one piece of
logic with a single one. The copies had drifted apart, and the drift was the cause.

## Fixed

- **Update templates dropped triples silently.** `INSERT { GRAPH <g> { … } } WHERE { … }`, `DELETE { … }` and
  `DELETE WHERE` kept at most 8 triples per `GRAPH` block, 4 `GRAPH` blocks and 32 default-graph triples, and reported
  only what they kept. `INSERT DATA` was not affected. Mercury MCP writes made with a longer template may have lost
  triples, with no record of which ones.
- **Update templates rejected object lists.** `{ <s> <p> 1, 2 }` was a syntax error. A property path in a template is now
  a syntax error too, as [51] TriplesTemplate requires; before, it could write nothing.
- **A sub-SELECT dropped projected variables and expressions past 8.** Its projection is now parsed by the query's
  SELECT clause parser: 16 variables and 8 expressions, with an error past either. REDUCED and the duplicate-name check
  now apply.
- **`LIMIT 0` returned every row** (SPARQL 1.1 §15.5: none), at top level, after ORDER BY, and in a sub-SELECT. LIMIT
  used 0 to mean "no limit".
- **`OFFSET n LIMIT m` ignored the LIMIT**, and failed in a sub-SELECT. [25] allows either order.
- **With GROUP BY, DISTINCT ran before grouping and never after it.** `SELECT DISTINCT ?o (COUNT(?s) AS ?n) … GROUP BY ?o`
  counted 1 where there were 2, and equal grouped rows came back twice.
- **A WHERE without triple patterns went to its own evaluator**, which read the flat parse:
  - it merged UNION branches into one row;
  - it dropped BINDs past 8 and FILTERs past 16;
  - `ASK {}` and `ASK { VALUES ?x { 1 } }` were false;
  - CONSTRUCT returned nothing;
  - LIMIT and OFFSET were ignored.
- **`COUNT(*)` over no solutions returned no row** (§18.5: one row with 0) whenever the WHERE had more than triple
  patterns.
- **A CONSTRUCT without top-level triples ran its template as the WHERE.** The executor guessed where the WHERE group
  started; the parser now records it.

## Changed

- One `LimitOffsetClause` carries LIMIT and OFFSET from the parser to the results, with an explicit "no limit". `LIMIT`
  or `OFFSET` without an integer is a syntax error.
- EXPLAIN no longer shows `LIMIT 0` on every plan.
- Removed: the evaluator for a WHERE without triple patterns, ASK's own evaluator, the brace-guessing methods, and the
  sub-SELECT's copies of the SELECT clause and LIMIT/OFFSET parsers. That is about 600 lines.

## Known issues

- **DESCRIBE has never described anything through the facade.** It runs the SELECT path and reads each row's first
  three values as a triple. The parser also skips DESCRIBE's target list, so `DESCRIBE ?s WHERE { … }` has no WHERE.
  This is [ADR-055](../adrs/mercury/ADR-055-query-where-one-parse.md) D3.
- **Mercury's W3C conformance runs only the SPARQL 1.1 manifests.** The 483 SPARQL 1.0 tests in the submodule are not run;
  one of them covers `LIMIT 0`.
- **DISTINCT compares rows by a 32-bit hash**, so two different rows can be merged as duplicates. This is unreproduced
  and inferred from the code.
- **`INSERT DATA` stores a bare number such as `1` in a different form from a WHERE's `1`**
  ([ADR-053](../adrs/mercury/ADR-053-one-rdf-term-one-atom.md)).
- **The flat WHERE parse still drops items past its capacities.** Queries are evaluated from the pattern tree, so only
  routing and EXPLAIN read it (ADR-055).
- Carried over: one debugger thread leaks per ended DrHook session on Linux; Windows lacks `RequestExit`.
