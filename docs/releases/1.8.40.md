# Sky Omega 1.8.40 — Mercury: a killed store keeps its committed writes; the MCP tool's output parses back. DrHook: why a crashing target can disable the debugger

**Released:** 2026-11-06
**Version bump:** `Directory.Build.props` → 1.8.40 (with these notes)
**Predecessor:** [Sky Omega 1.8.39](1.8.39.md) — Mercury: parsers read short reads and a byte order mark; one literal
split; one writer per results format.

## Headline

**A Mercury store killed after a commit keeps the write** ([ADR-058](../adrs/mercury/ADR-058-wal-replay-restores-consistent-store.md),
Accepted). The atom store's header was saved only in `Dispose`, which a killed process never finishes. On restart
the write was lost, and the next session reused atom IDs, so older quads resolved to newer terms. That is what
damaged elite's memory store. A commit now makes its atoms durable before the WAL commit that references them.

**`mercury_query`'s output parses back.** The MCP tool wrote its results itself. Graph results joined the stored
terms with spaces, and SELECT rows joined them with tabs, so a quote, a backslash, a tab or a line break in a
literal left output that no reader could read. Both now go through the writers the CLI and the HTTP endpoint use.

**DrHook: the cause of the debugger hangs is located** ([ADR-016](../adrs/drhook/ADR-016-debugger-resilience-and-recovery.md),
Steps 0 to 4). A target that dies while mscordbi waits on a request to it leaves that wait blocked for good, and
the debugger's process with it. mscordbi's PAL checks the target's process handle when a wait starts and starts no
thread to check it again ([finding 105](../../poc/drhook-engine/findings/105-dll-pal-never-rechecks-a-waited-process.md)).
Ending a session at a crash's stop avoids it; a missing `ProcessExited` stop detects it; only a new process recovers
from it. The worker process that does that is decided, not yet built.

## Fixed: a killed store keeps its committed writes (ADR-058)

- `CommitBatch` and the single-write paths flush the atoms (data, offsets, hash table, header) before the WAL commit
  that references them. `FlushToDisk` does the same for bulk load.
- `BTreeFile` records the transaction its saved entry count is exact for; replay counts the entries a crashed
  process inserted after it.
- The checkpoint saves atoms and counts durably before it truncates the WAL.
- At open, `HashAtomStore` takes atom records past a stale header, so no ID on disk is reused. A chain that continues
  and then breaks (ID reuse) makes the store refuse writes.
- A damaged store refuses a batch before it writes the WAL. Each refused INSERT grew the WAL by one record with no
  commit; replay ignored it, but a store that refuses writes should write nothing.

Cost on zbook's NVMe: a single `AddCurrent` with new terms went from 4.0–4.3 ms to 6.5–6.8 ms; a `CommitBatch` of
50 is within noise. Open in ADR-058: Graph-profile counts, the trigram index, the leaf-split window and Windows power
loss.

## Fixed: a stop signal no longer ends mercury-mcp while it closes the store

`RunAsync` disposes the host, which removes its SIGINT and SIGTERM handlers. Claude Code sends SIGTERM 100 ms after
SIGINT; on a slow machine it arrived during `pool.Dispose()` and ended the process before the store was closed.
mercury-mcp now keeps its own handlers until `Main` returns. On zbook, with a SIGTERM delivered inside `Dispose`, the
old build was killed 6 of 6 times and the new one closed the store and exited 0 6 of 6 times (ADR-058 Q7).

## Fixed: mercury_query's output parses back

- **CONSTRUCT and DESCRIBE** write N-Triples through `RdfEngine.WriteTriples`. Found while rebuilding elite's store:
  a comment containing `{"success":true}` could not be inserted again from the tool's own output.
- **SELECT** writes SPARQL 1.1 TSV through `SparqlCsvResultWriter`: a `?var` header, terms in SPARQL syntax with
  `\"`, `\\`, `\n`, `\t` and `\r` escaped, and an empty field for an unbound variable.

## Changed output

- `mercury_query`'s SELECT output starts with a `?var` header, and a query with no rows prints the header and
  `0 result(s)` instead of `No results`.

## Fixed: REGEX and REPLACE have a one-second limit per match

Every regex was built with a fixed 100 ms match timeout, which failed a trivial REPLACE on a loaded CI runner. The
limit is one second everywhere (`RegexMatchLimit`); a costly pattern still fails its query.
[ADR-060](../adrs/mercury/ADR-060-query-time-limit-and-cancellation.md), a query's time limit and its cancellation,
is Deferred.

## Fixed: DrHook's Detach accepts both gone-target codes

`DebugSession.Detach` named `0x8013134F` `CORDBG_E_PROCESS_TERMINATED`; it is `CORDBG_E_OBJECT_NEUTERED`, and
`PROCESS_TERMINATED` is `0x80131301`. So Detach reported the real "terminated" as an unexpected anomaly. Both mean
mscordbi is finished with the target, and Detach accepts both. It then waits up to 500 ms for the OS to confirm the
target exited, and reports the new `GoneTargetAlive` anomaly if it is still running.

## DrHook: ADR-016, how a debugged program ends

ADR-016 (Proposed, the experimental charter) asks what each way a target ends does to the debugger, on each
platform, before deciding the lifecycle. Steps 0 to 4 ran in this release, as probes 100 to 102 in
`poc/drhook-engine`, on omega and its two VMs, and probes 101 and 102 also on the six CI runners (the `DrHook probe`
workflow, started by hand; probe 100 is added to it):

- [Finding 100](../../poc/drhook-engine/findings/100-orphaned-transport-read-holds-dac-lock.md): a target that dies
  while mscordbi's event thread reads its memory leaves the DAC locked; every later attach hangs (macOS).
- [Finding 101](../../poc/drhook-engine/findings/101-platform-facts.md): how mscordbi reads a target's memory depends
  on the target's ancestry on Linux, and on the machine and the target's executable on macOS.
- [Finding 102](../../poc/drhook-engine/findings/102-natural-end.md): a target that ends by itself leaves DrHook
  usable on every machine.
- [Finding 103](../../poc/drhook-engine/findings/103-terminate-waits-on-error-write.md): `Terminate` waits forever on
  an error write to a target that is gone (macOS).
- [Finding 104](../../poc/drhook-engine/findings/104-crash-boundary.md): a target that crashes by itself can leave
  the debugger unusable, with or without the runtime's warning; ending the session at the crash's stop avoided it.
- [Finding 105](../../poc/drhook-engine/findings/105-dll-pal-never-rechecks-a-waited-process.md): the mechanism behind
  100, 103 and 104.

On macOS and Linux arm64 a crash continued past its stop hung the debugger in up to half the runs; ending the session
at the stop was clean every time (120 of 120), and a `ProcessExited` stop came within 34 ms of every end that left
the debugger usable and never after one that did not. On Windows arm64, which has no PAL and no transport, no run
hung (130 of 130).

**Decided** (Martin, 2026-11-06): the debugger runs in a worker process, and relaunching it is done by process
indirection. Some crashes give no stop at which to end the session, and nothing inside the process can wake the
blocked wait. Avoidance and detection stay, so a worker is discarded rarely and for a known reason. Step 5 proves
the design.

## CI and the solution

- A push to main no longer cancels another push's run; two hosts push, and one cancelled the other's Windows jobs.
- A check that the solution lists every ADR; the 32 missing ADRs are listed, and the Cognition and Surfaces folders
  are restored.
- The macOS runners record the stacks of a hung DrHook integration test.

## Tests

- New project `tests/Mercury.Mcp.Tests`: the tool's CONSTRUCT, DESCRIBE and SELECT output with quotes, a backslash,
  a line break and a tab parses back to the stored terms.
- `CrashRecoveryTests` with `tests/Mercury.CrashTarget`, a process that writes and kills itself (10 cases, all failed
  before the fix).
- Three races between a test and the thread it watches, two of which failed once each on Windows arm64 CI.
- A temporal test that assumed an add and a delete finish within a second.
- The DrHook VSTest-target tests write a timeline; the flood waits are bounded.
- Full suite on omega: 6,681 tests, 0 failed, 169 skipped.

## Known, not fixed

- A target that dies during a request leaves the DrHook debugger unusable in its process (finding 105), until the
  MCP server is restarted. Ending at a crash's stop avoids it for crashes the runtime warns about; the worker process
  (ADR-016 Step 5) is the recovery.
